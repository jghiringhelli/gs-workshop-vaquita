# ADR-001: Repository Pattern for Data Access Layer

**Date:** 2026-04-10  
**Status:** Accepted

## Context

The Tanda API needs a clear separation between business logic and data persistence. The spec explicitly requires that route handlers must not contain SQL, and services must call repositories — not the database directly.

We evaluated two approaches:
1. **Active Record** — domain objects that query the database themselves
2. **Repository Pattern** — dedicated classes that encapsulate all database access

## Decision

We adopted the **Repository Pattern** with a three-layer architecture:

```
routes → services → repositories → db
```

- `repositories/` is the **only** layer allowed to call `db.prepare()`, `db.run()`, `db.get()`, `db.all()`
- `services/` contains all business rules and calls only repositories
- `routes/` only validate input (Zod) and call services

## Consequences

**Positive:**
- The `Bounded` scoring criterion is naturally satisfied — zero `db.*` calls in route files
- Business rules live exclusively in services, making them testable in isolation
- Swapping SQLite for another database only requires touching the repository layer
- The `Composable` scoring criterion is satisfied because HTTP handlers contain no logic

**Negative:**
- More boilerplate than Active Record for simple CRUD
- Slightly more files to maintain

## Alternative considered

Using `better-sqlite3` directly inside Express route handlers would have been faster to write but would fail the `Bounded` (2pts) and `Composable` (3pts) scoring criteria — 5 points we cannot afford to lose.
